## 3quater. L1 fetchs `_source` parallèles (2026-07-18/22) — gain MODESTE, défaut OFF

Implémentation `18e1c25` : `SURCH_SOURCE_FETCH_PARALLEL=1` hydrate les gagnants top-k via
`rayon::par_iter` dans `documents_by_internal_ids`; `collect` indexé puis filtrage séquentiel
préservent l'ordre. Le `pread` positionné sur `Arc<File>`, la side-table packée lue par valeur et
les décompresseurs zstd thread-local sont compatibles. **Oracle local packing+zstd+parallèle :
0 divergence** ; CI et docker-build verts. Le flag absent/0 garde strictement le chemin historique.

A/B 28,9M@6g sur PRO2-M calme, même image `sha-18e1c25…`, packing+zstd, deux passages
contrebalancés (A H0→H1, B H1→H0), seul le flag change :

| Sonde (p50/p95/p99) | Passage A H0→H1 | Passage B H1→H0 | Poolé H1/H0 |
|---|---:|---:|---:|
| fixe | −8,3 / −4,7 / −4,8 % | −12,0 / −4,7 / −5,3 % | **−10,1 / −4,7 / −5,1 %** |
| aléatoire | −15,1 / −5,5 / **+2,1 %** | −10,9 / −3,1 / **+5,2 %** | **−13,0 / −4,3 / +3,7 %** |
| froide | −6,5 / −9,4 / −6,7 % | −2,7 / **+3,6 %** / −2,6 % | **−4,6 / −3,3 / −4,7 %** |

Le p50 aléatoire s'améliore dans les deux ordres (22,79 → 19,83 ms poolé), donc l'association est
reproductible, mais le `/2–3` attendu est **réfuté** : l'hypothèse « 10 × 2,8 ms de pread dominent
le p50 » était inférée, pas instrumentée. Amdahl s'applique (parsing HTTP/DSL, postings, scoring,
allocations, decode/JSON restent séquentiels), le pool Rayon a un coût, et dix lectures du même
`source.dat` ne gagnent pas linéairement sur une file SBS.

Limite méthodologique décisive : avec le mapping 28M `NOM/PRENOMS`, la sonde fixe historique
requête `nom:MARTIN`, donc **zéro hit et zéro hydratation réelle**, mais elle bouge presque autant
que la random. Une partie du −13 % brut est donc un déplacement de baseline et non un effet
causal `_source`. La « cold » ne reclaim qu'une fois avant 1000 requêtes et se réchauffe ensuite ;
le p95 change de signe et le p99 random régresse dans les deux passages. **Verdict : flag OFF par
défaut**, mode expérimental opt-in conservé ; aucune claim tail/cold ni fermeture du front ES.

**L2 minimale avant tout nouvel algorithme** : instrumentation benchmark-only par requête autour
de `documents_by_internal_ids`, `SourceStore::read`, decode zstd et parse JSON (`fetch_wall_us`,
somme/max `pread_us`, `decode_us`, `json_us`, IDs/octets/threads) ; latences brutes conservées ;
témoin non hydraté `size:0` ; 50 cold avec reclaim vérifié avant CHAQUE requête. Trois paires
contrebalancées. Gate default ON : oracle 0 ; témoin dans ±3 % ; random p50 poolé ≤−10 % avec
borne IC95 ≤−5 % ; `fetch_wall_us` p50 (≥8 hits) ≤−20 % ; borne haute IC95 p95/p99 ≤+3 %.
L1 échoue déjà ce dernier gate (random p99 +3,7 %).

## 3quinquies. L2 instrumenté sur volume OVH `classic` (2026-07-25) — LE FRONT N'EST PAS LE `_source`

**Où** : instance OVH Public Cloud GRA11 `b3-16` (4 vCPU / 16 Gio — quotas projet : 6 cœurs,
25 Gio RAM, 30 Gio volume, dont 2 vCPU + 8 Gio déjà pris par le node K8s), **volume bloc de type
`classic`** — le type exact derrière le `storageClassName: block-standard` posé sur les Jobs K8s
par la PR #9. Docker relocalisé (`data-root`) sur ce volume : **l'index Surch et `source.dat` sont
donc sur le stockage cible**, le corpus NDJSON restant sur le disque système local (lu à
l'indexation seulement, jamais pendant les sondes). `CPUSET=0-2`, `MEM_LIMIT=6g`, packing+zstd,
image `sha-56bf32f…`, corpus 28 917 511 docs, disque 12 296 Mio (`_source` 7 248 Mio).
Chiffres absolus non comparables aux runs SBS (3 cœurs vs 8, stockage différent) — ce qui compte
ici est la **décomposition par phase** et la comparaison interne H0/H1.

**Décomposition d'une requête aléatoire `size:10` (H0 séquentiel, 1000 requêtes, `size:10`)** :

| Poste | p50 | p95 |
|---|---:|---:|
| Requête HTTP complète | 12,72 ms | 191,57 ms |
| dont hydratation `_source` (`fetch_wall`) | **3,70 ms (29 %)** | **6,86 ms (3,6 %)** |
| dont `pread` (somme) | 3,57 ms | 6,71 ms |
| dont décompression zstd | 0,04 ms | 0,08 ms |
| dont parse JSON | 0,06 ms | 0,11 ms |
| **reste : recherche, scoring, HTTP** | **9,02 ms (71 %)** | **184,7 ms (96 %)** |

Le **témoin sans hydratation** (`size:0`, mêmes corps, court-circuit vérifié côté moteur) le
confirme indépendamment : **1,54 ms p50 / 185,66 ms p95** sans lire un seul `_source`.

**H1 (parallèle) prouve le mécanisme ET son insuffisance** : `fetch_wall` p50 passe de 3 699 à
1 713 µs (**÷2,16**, 3 workers Rayon effectifs — le gate mécanisme « `fetch_wall` p50 ≤ −20 % »
passe très largement), mais la requête complète ne gagne que **−9 %** au p50 (12,72 → 11,58 ms)
et **+2,4 %** au p95 (191,57 → 196,26). Amdahl vérifié expérimentalement : 29 % × 54 % ≈ 16 %
de gain théorique maximal au p50, 9 % observé.

**Conclusions (elles réorientent le programme)** :
1. **L'hypothèse fondatrice de L1 est réfutée quantitativement** : les lectures `_source` ne
   dominent pas la latence (29 % du p50, 3,6 % de la queue). Le `−13 %` / `+3,7 %` de L1 était
   exactement ce que cette proportion permet — ni bug, ni artefact.
2. **La queue de latence appartient au chemin de RECHERCHE** (postings, scoring), pas au stockage
   des documents : 96 % du p95. C'est LE front à instruire pour rattraper ES (58,8 ms p95 au
   triptyque §3bis).
3. zstd et JSON sont négligeables en lecture (< 1 % chacun) : la compression 2b ne coûte rien au
   read-path, elle ne fait qu'économiser du disque.
4. `SURCH_SOURCE_FETCH_PARALLEL` **reste OFF** : 9 % de p50 contre une régression p95 et de la
   contention. À réévaluer seulement si le chemin de recherche est optimisé — le `_source`
   deviendrait alors proportionnellement dominant.

**Deux défauts du harnais, détectés FAIL-CLOSED** (le protocole a refusé de publier des chiffres
faux, comportement voulu) : (a) l'export du JSONL par phase ne fait pas avancer son offset — les
tranches exactes ont été recalculées à la main depuis
`surch.source_fetch.profile.snapshot.jsonl` pour les tableaux ci-dessus ; (b) la sonde froide
exige root sur le cgroup (`memory_reclaim_write_failed_before_request_1`) : le harnais tournait
sous `ubuntu`. Le court-circuit du témoin, lui, est prouvé correct côté moteur (le serveur n'a
produit aucune entrée de profil pendant la phase témoin). Ces deux points sont à corriger avant
tout nouveau run L2.

Artefacts : `~/.cache/fair-ab/l2-ovh-classic-2026-07-25/{h0,h1}/` (scorecards + JSONL par
requête). Instance et volume OVH détruits après collecte.
